Separation of duties

Keep the brief separate from the agent that acts.

Your Class 4 automation keeps running exactly as it is. Today you add a second part that picks up its output.

7:00 · Class 4 automation

Dictated steps. It reads your sources and saves the brief to your folder. It never acts.

7:30 · Class 5 agent

A goal, not steps. It finds that file, decides what each item needs, acts within your limits, and writes the handoff.

🧩

Each part is managed on its own. Change what the brief pulls without touching the agent; tighten the agent's limits without touching the brief. Each has its own sessions, cost, and cap, so you always know which one broke.

The test for which is which: can you write the steps down before you see what arrives? If yes, it's an automation. If the next step depends on what it finds, it's an agent.

What the agent can reach for

Tools are what the agent uses to act.

An automation calls the same things in the same order. An agent picks the tool each item needs, when it needs it. In Managed Agents, its tools come three ways:

🧰 Built-in tools

Ready on every agent: a shell, reading and writing files, searching, web search and web fetch.

🔌 MCP servers

Your apps. The same connections as Class 4, plus the ones that act: drafts, events, tasks.

🌐 API calls

Any service with an API, called with a token from your vault. For apps with no MCP server.

🐍

In Class 6, a fourth kind: your own Python scripts. In OpenClaw you can write a script and hand it to the agent as a tool. Managed Agents can't run that for you: next slide.

Where Managed Agents stops

Custom tools need your code running somewhere.

In Create agent, Add custom tool asks for three things: a name, a description of when to call it, and an input schema. There's no box for the code.

⏸️ What happens when it's called

The run pauses and waits for your own application to run the code and send back the result. In a scheduled run, nothing answers, so it waits.

🔓 Where that changes

In Class 6 you get a place where your own code runs, and a script becomes a real tool your agent can call.

Every surface has limits. Knowing where this one stops is how you'll know when a job needs the next one.

Read this before anything runs

Agents cost more than automations. Cap every run.

An automation runs the same steps every time. An agent chooses its own: it looks things up, retries, searches the web, and can hand work to other agents. Each of those is more usage.

You can't list every case, so give it limits

For each kind of item, decide how far it can go.

You can't write a step for every email that might arrive. So instead of steps, you give it four lists. This is the heart of the agent's system prompt.

✅ Handle it

Do it and report after. Scheduling requests, filing follow-ups as tasks.

📝 Prepare it

Get it ready; you finish it. A reply drafted in Gmail that you read and send.

✋ Bring it to me

Only you can decide. Money, clients unhappy, anything about your team.

🚫 Leave it alone

Don't touch it. HR, legal, anything personal.

🛡️

It reads email from strangers, and an email can try to give it orders. The lists and the tools you turn off are what stop that. Nothing goes out as you: it drafts, you send.

Create agent, top to bottom

Step 1: Name it, pick the model, write its directions.

Managed Agents → Agents → Create agent. Fill in General: a name, the model and effort, a description, and the system prompt. Start the system prompt from this and fill in the brackets:

You run my mornings. I'm [role] at [company]. What matters to me: [who and what gets priority; carry over your Class 4 rules].

Each morning, find today's brief in my [Drive / Dropbox] folder and work through each item using my lists. If there's no brief today, say so at the top of the handoff. Handle: [kinds of items]. Prepare (draft, never send): [kinds]. Bring to me: [kinds]. Leave alone: [kinds]. If unsure, bring it to me.

After each action, check it really happened. Read the handoff log first and update it last. Save the handoff to my [Drive / Dropbox] folder, dated: Taken care of, Needs your action, FYI.

Model: a Sonnet model at low effort is a good start. Raise it only if the calls it makes are weak; higher effort costs more per run.

What it may use, and how

Step 2: Add its tools and set each permission.

Open Tools. The built-in toolset is already there, with its permission set to Auto. Then add an MCP server for each app it reads or acts in, including the folder where the brief lands.

✅ Always allow

The built-in tools, the reading tools, and the actions your lists need: creating drafts, filing tasks, saving the handoff. It runs unattended, so nothing can wait on a click.

🚫 Turned off

Send, anything that deletes, and any action your lists don't need. A tool that's off can't be called, whatever an email says.

Logins work as in Class 4: each new MCP server asks for a credential, and plain Connect is usually enough.

The last two sections of the form

Step 3: Leave Skills and Multiagent empty, on purpose.

Skills: the briefing skill stays with the Class 4 agent. This agent only needs the file it produces. That's the separation that lets you change one without the other.

👥 Multiagent: subagents

Other agents it can hand work to, like a researcher. Useful later. Each one is another run on your bill.

🧑‍⚖️ Multiagent: advisor

A second model it can consult on hard calls, billed at that model's rates against the same cap.

Get one agent working before you give it a team. Then click Create agent.

So it doesn't rediscover the world every run

Step 4: Give it a memory store for its log.

Every run starts fresh. Without a record, it would draft the same reply twice and forget what's waiting on you. A memory store fixes that: Managed Agents → Memory stores → new store, called handoff-log.

📒 What goes in the log

What it handled, what it prepared, what's waiting on you, and what changed since the last run. It reads the log first and updates it last.

🔎 Yours to read

You can open the store in the Console and read or fix any entry. You'll attach it to the deployment in Step 6.

Run it, read it, fix it

Step 5: Test-run it and check it really acted.

Start a test run and give it this morning: "Handle my morning." Watch the session, change the config where something's off, and run it again.

  • 1. Read its choices → it found today's brief, then picked a different tool for each item. That's the agent deciding its own steps.
  • 2. Check it acted → the draft is in Gmail, the task is on your list. "I created the draft" isn't a draft you can open.
  • 3. Check the lists → does "needs your action" hold only what needs you? Fix the lists in the system prompt, not the handoff.
  • 4. Read the cost → compare it to a Class 4 run. Multiply by 22 weekdays.
The timer wakes it; the agent decides the rest

Step 6: Deploy the agent at 7:30, after the brief.

Managed Agents → Deployments. Leave the Class 4 deployment as it is, and create a second one:

  • Agent: the one you just built. Environment and vault: the ones from Class 4.
  • Memory store: handoff-log.
  • Schedule: 30 7 * * 1-5 (weekdays at 7:30) and your time zone. If the brief sometimes lands late, move this later, not earlier.
  • Prompt: "Handle my morning." A goal, not steps.
  • Budget: a per-run cap, a little above what your test run cost.

Click Run now once, and read the session. It's the first run with nobody approving anything, so it proves your permissions hold.

The first week is calibration

Move items between lists until the handoff is right.

📥 Too much reaches you

Things you'd handle the same way every time. Move that kind of item to handle or prepare.

📤 Too little reaches you

It handled something you wanted to see. Move it to bring to me, and say why.

🔍

Surprised by something it did? Open that run's session and read why. Then fix the cause: a list in the system prompt, a tool's permission, or a wrong entry in the log.
